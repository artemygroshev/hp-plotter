# Удалённая очистка головок HP DesignJet 500

Цель — запускать штатную процедуру HP с BTT и видеть её фактические этапы.
Найденные функции прошивки и готовая автоматическая очистка — разные результаты.
Полностью автоматический цикл пока не принят на плоттере.

## Проверенный путь HP

В [User Reference Guide HP](https://h10032.www1.hp.com/ctg/Manual/c00748239.pdf),
страницы PDF 72–75, описан `Ink → Troubleshooting`. Плоттер проверяет
выравнивание, печатает диагностические образцы и спрашивает об их качестве.
Выбор дефектного цвета ведёт к попытке очистки; внутри одного прохода HP
ограничивает число попыток тремя. Новый цикл не должен автоматически начинаться
после неудачи. Результат печати оценивается по бумаге.

В исследованном случае после ручной диагностики экран сообщил об ошибке
выравнивания из-за головок и предложил Enter для списка неисправных головок.
Поэтому переход к новой процедуре должен сначала учитывать этот экран.
Пустая очередь CUPS и окончание движения каретки не доказывают Ready.

## Один шаг через виртуальную кнопку

[panel_keys.py](../tools/service/panel_keys.py) — отдельный операторский инструмент,
не кнопка очистки в GUI и не автоматический сценарий. Разрешены только `ENTER`,
`BACK`, `UP`, `DOWN`, `TOP`, строго одна кнопка за вызов. Комбинаций, `ALL`,
`PAPER`, `CANCEL` и произвольных Tcl-команд нет.

Этот CLI предназначен только для неподвижного основного буфера: при включённом
мигании или активной второй фазе он останавливается до кнопки. 9 ноября во
втором буфере прочитано `Printhead warning / Poor print quality`, тогда как
основной содержал экран выравнивания. Поэтому один буфер нельзя объявлять всем
текущим экраном или признаком Ready. Для такого состояния нужен разбор обеих
фаз оператором; эта процедура отличается от данного одно-кадрового CLI.

До ввода инструмент:

1. Берёт общий USB-lock и durable guard; требует пустую очередь, отсутствие
   чужих USB-дескрипторов и известный адаптер none/alt0.
2. Проверяет class-ID при захвате интерфейса и перед каждым запросом, firmware
   A.04.02 и serial. Каждый запрос проверяет также USB-узел, binding, machine/boot,
   очередь и владельцев. Только пустой class-ID допускает ограниченный повтор:
   максимум восемь чтений с паузами 0,1/0,3/0,8 с между парами. Другой ID или
   отрицательная ошибка USB останавливают операцию. Это не повтор Tcl-команды.
   Вариант с одним ID на весь сеанс отвергнут: FW прошёл, ответ serial не пришёл;
   его незавершённый поток отдельно закрыт стандартным UEL/PJL EOJ и архивирован
   как оставленное чтение, без заявления об успешном serial или очистке.
3. Сверяет пять диапазонов кода/таблиц с закреплёнными SHA256 и проверяет, что
   callback клавиатуры установлен в пределах кода engine.
4. Снимает полный LCD128×64 и требует заданный оператором SHA256. Изменившийся
   экран останавливает ввод; новый снимок сохраняется для разбора. HP busy тоже
   останавливает ввод.

Затем отправляется один `fpSimulateKey`, проверяется свежий ответ с nonce и
снова читается полный LCD. Для native-вывода разрешена только точная
предшествующая строка `Simulating: <выбранная кнопка>`; другой текст, другая
кнопка или дублированная строка отвергаются. Сырые принятые байты сохраняются. Получение `0` не означает начала очистки. Потеря
ответа, неполная запись или отсутствие снимка после действия запрещают повтор
и сохраняют guard. Даже прочитанный экран не объявляется атомарным снимком
движущегося изображения или всеми фазами мигания.

Пример на настроенной BTT, из каталога проекта (только после просмотра текущего
полного кадра и выбора действия):

```sh
sudo env HP_PLOTTER_CONFIG=/etc/hp-plotter/config.json \
  python3 tools/service/panel_keys.py --key ENTER \
  --expect-lcd-sha256 SHA256_ТЕКУЩЕГО_ПОЛНОГО_LCD \
  --until-utc YYYY-MM-DDTHH:MM:SS+00:00
```

Используйте `panel_keys.py` вместе с `batch_usb.py` из той же версии проекта:
старый модуль только для чтения не имеет интерфейса `command_payload`.
Несовместимость проверяется до открытия USB. Для проверки на существующей BTT
оба файла размещались в отдельном приватном каталоге; текущий GUI не заменялся.

Нужен явный предел времени на 300–1200 секунд вперёд. Каждое следующее
нажатие выбирают по новому экрану; запускать заранее угаданную цепочку нельзя.
Чтение через этот USB–parallel-мост медленное и пока не доказано устойчивым.

## Что найдено офлайн в A.04.02

Исходный engine: SHA256
`c882e68d2eb2462745f1ec984ce8f5ed745d2900587dce6b36acee5b89a1f4eb`,
M68K big-endian, база `0xa0001000`. Бинарный файл HP не распространяется.

| Точка | Результат анализа | Ограничение |
| --- | --- | --- |
| `fpSimulateKey` | Штатный разбор имён кнопок и вызов callback клавиатуры | Проверка на реальном HP проводится отдельно |
| `fpMenuFocus` | Отправляет событие изменения фокуса меню | Аргументы/идентификаторы меню не приняты; не вызывается |
| `svsOnIntervention_set` | Принимает уровень, передаёт его в механический recovery | Аргумента цвета нет; прямая команда не включена |
| `ssSpit`, `ssWipePens`, `ssScrubPens` | Низкоуровневые параметры сопел и механики | Не заменяют полную процедуру HP; не вызываются |
| IQ state `0xa03a4610` | Есть именованные этапы процедуры | Сам по себе старый state не доказывает активную работу |

Состояния IQ: 0 INITIALIZING; 1 PRINTING_IMAGE_QUALITY_DIAGNOSTIC;
2 PRINTING_PRINTHEAD_HEALTH_DIAGNOSTIC; 3 UNLOADING_PRINT;
4 CLEANING_PRINTHEADS; 5 CLEANING_DONE; 6 WAITING_FOR_USER_ANSWER.
При чтении дополнительно нужны активность work/UI, cancel-флаг и текущий экран.
В реальном снимке прочитано state6 при ui_handle0/eventffffffff и экране
ошибки выравнивания: это не активная очистка.

Статический путь IQ передаёт выбор цветов для экранов и учёта результатов,
но механическая процедура использует также маску `0x0f`. Из этого нельзя
заключить, что физические движения и расход чернил затронут исключительно
выбранную чёрную головку. Полностью отдельная K-прочистка ещё не доказана.
Прямой вызов recovery также обходил бы часть штатного UI и учёта; он не включён.

## Приёмка

Для завершения нужны: фактический переход по меню, штатный запуск,
наблюдение этапа очистки и её завершения, отсутствие дублированного ввода,
чистый USB cleanup и один [TrueBlack-тест](black-output-check.md) после цикла.
Показ экрана, получение ответа кнопки и успешная передача теста — разные
проверки. Ни одна отдельно не доказывает восстановления чёрного канала.

На этапе испытаний 9 ноября пять попыток остановились до передачи кнопки:
потеря class ID, отсутствие свежего serial/FW, отказ старого read-only модуля
и прерванный OUT при чтении LCD. Полный экран ошибки и пять диапазонов кода
на HP прочитаны, но это не приёмка ввода. Прерванные собственные чтения
разобраны отдельно; один раз сброшен только USB-мост, без Printer Class
SOFT_RESET. Поздний ответ старого запроса был отвергнут по nonce.
