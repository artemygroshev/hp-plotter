# Один USB-сеанс на сбор

`batch_read.py` — отдельный экспериментальный способ чтения для **C7769B /
A.04.02 / 1a86:7584**. Он держит один USB-дескриптор и alt1 на весь сбор,
а свежий IEEE1284 ID проверяет перед каждым запросом. В конце восстанавливает
свободный интерфейс alt0. Это уменьшает число переключений интерфейса;
устранение всех тайм-аутов пока не доказано.

## Зачем появился этот вариант

Прежний способ открывал и восстанавливал USB после каждого короткого запроса.
Профиль 129 байт выдержал девять полных циклов, затем снова остановился на
неопределённом обмене. Вариант с одним дескриптором, но ID только в начале,
не получил свежего ответа уже на третью команду. Повторный ID перед каждой
командой — существенная часть следующего опыта, а не необязательная оптимизация.

Отдельно приняты два реальных сбора этого варианта:

| План | Проверенный результат |
| --- | --- |
| `diagnostics` | 17 запросов, 14 дополнительных полей, 111,325 с |
| `all` | 73 запроса, 30 полей, три полных буфера LCD, 504,318 с |
| `journal` | 20 запросов, десять системных событий, 133,463 с |
| `head-journal` | 35 запросов, история четырёх цветов, 228,192 с |

Сверены исходные ответы, свежие метки, два реально выполненных пустых этапа IN
после каждого ответа, все ID, USBmon, завершение сеанса и каждый пиксель LCD.
USBmon подтверждает границу Linux/HCD, а не содержимое параллельного провода.

Последующий v13-монитор отказал после восьми успешных запросов. Один descriptor
и ID перед каждым запросом **не устранили** проблему. Новая гипотеза меняет
только размер COMMENT с 64 на 63: тогда и primary 129, и COMMENT заканчиваются
коротким USB-пакетом при maxPacketSize=64. Она выбирается явным `--short-comment`
или настройкой `comment_bytes: 63`, с новой серией и новым run_id. По умолчанию
сохранены 64 байта. Наличие короткого пакета не доказывает устранение сбоя.

Новый профиль 129/63 отдельно прошёл `diagnostics` 17/14/0 за 112,665 с и
полный расширенный сбор **87/44/3 за 758,171 с**. Оба результата приняты по
сырью, исходникам, трассе и cleanup; все LCD-пиксели сверены. Длительный монитор
после этого запущен новой серией. Успех короткого опыта не подменяет её итог.

## Разовое чтение на BTT

Нужна подготовленная [локальная установка](monitor.md), `executor: "local"`,
`idle_driver: "none"`, `small_query_bytes: 129`, закреплённые идентификаторы,
пустая очередь, свободный интерфейс и отсутствие неопределённого guard.
Оба монитора должны быть остановлены. Работайте из каталога выбранной версии.
`DEADLINE` — разрешённый срок ISO8601 с часовым поясом.

```bash
export HP_PLOTTER_CONFIG=/etc/hp-plotter/config.json

python3 tools/service/batch_read.py diagnostics --refresh-id --until-utc "$DEADLINE"
python3 tools/service/batch_read.py all --refresh-id --until-utc "$DEADLINE"
python3 tools/service/batch_read.py all --include-diagnostics --refresh-id --until-utc "$DEADLINE"
```

Это три отдельных выбора. Последний запрашивает 87 ответов / 44 поля / три
буфера, сохраняя один USB-сеанс. Не запускайте несколько команд одновременно.
После неопределённого ответа следующая команда запрещена общим guard.

Приватный `*-batch.json` содержит общий preflight/postflight, USBmon,
управляющие запросы и cleanup. `*-query-NNN.json` содержит ответ одной команды.
`stream_closed` в подзапросе означает доказанную границу сообщения; восстановление
USB доказывается только один раз в конце всего сеанса.

## Согласование с CUPS

Один flock и один guard удерживаются на весь сбор. Между запросами проверяются
очередь, личность адаптера, `usbfs`/alt1 и единственный свой владелец USB.
Если пришло задание, сборщик завершает текущий ограниченный ответ, восстанавливает
интерфейс и уступает печати. Появление задания отделено от результата аппаратного
cleanup. Чужой дескриптор или неизвестный драйвер останавливают чтение.

`usbfs` во время libusb claim — ожидаемое состояние Linux. Это отличается от
требуемого `driver=None` между сеансами. Ответ GET_INTERFACE у исследованного
моста может показывать 0, когда хост реально выбрал alt1; в отчёте сохраняются
оба значения, проверяется также sysfs хоста.

## Монитор и отдельная серия

`batch_monitor.py` использует прежний ограниченный цикл публикации кэша. Для
него предусмотрен отдельный `deploy/hp-plotter-batch-monitor.service` и приватный
`/etc/hp-plotter/batch-monitor.json`. Параметры прежнего шаблона дополняются:

```json
{
  "run_id": "UNIQUE_NEW_RUN",
  "release_id": "SELECTED_IMMUTABLE_RELEASE",
  "until_utc": "AUTHORIZED_ISO8601_DEADLINE",
  "interval_seconds": 900,
  "minimum_cycle_window_seconds": 900,
  "view_root": "/var/lib/hp-plotter/view",
  "include_diagnostics": true,
  "refresh_id_each_query": true,
  "comment_bytes": 64
}
```

Перед заменой сохраните прежний кэш и настройки. Старый монитор должен завершить
cleanup и быть неактивным; новый запускается отдельно, с новым run_id. Не
объединяйте счётчики разных способов в непрерывную успешную серию. Период 900 с
выбран для отдельной ночной проверки; уместный период зависит от длительности
сбора и допустимой задержки данных. Оба монитора одновременно не запускаются.
Автоматический reset, снятие неопределённого guard и повторы команд отсутствуют.

## Журнал системных ошибок

Отдельный план `journal` читает существующее RAM-зеркало MAIN, без вызова
EEPROM-функций, выделения памяти на HP, записи или очистки истории:

```bash
python3 tools/service/batch_read.py journal --refresh-id --until-utc "$DEADLINE"
python3 tools/service/batch_read.py head-journal --refresh-id --until-utc "$DEADLINE"
```

Он требует совпадения четырёх участков машинного кода A.04.02, версии таблицы 6,
11 дескрипторов, допустимых указателя/длины и двух одинаковых полных копий
201-байтового кольца. Заголовки проверяются повторно. Читатель сохраняет код
`XX:YY`, исходный файл, строку и сырой date field. Единицы даты ещё не подтверждены.
История не объявляется текущей причиной ошибки. Аппаратный результат и статус
сравнения со штатным меню указаны в [проверке](validation.md).

Для головок читаются 302 байта: индексы и двадцать 15-байтовых слотов. Native
getter индекса не вызывается: он может сам записать EEPROM при неверном индексе.
Расход в cc, время в днях и cleaning level следуют формату меню HP; они не
доказывают реальный календарный возраст или заполнение внешних ёмкостей.

После приёмки готовой сессии можно опубликовать только очищенный кэш. Команда
ниже USB не открывает:

```bash
python3 tools/service/journal_view.py --session /private/readonly-session-TIMESTAMP.json --view-root /var/lib/hp-plotter/view
```

HTTP `/api/system-journal` и `/api/head-history` возвращают эти выборки с их
собственным возрастом. Веб-серверу не передаются исходные ответы, пути captures,
идентификаторы платы, пароль или уникальные идентификаторы головок.
